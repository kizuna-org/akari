# 05. 実装の進め方と検証

## 先に固定しないもの

感情マイルストーンの配置と振る舞いの具体的な合格条件、最初の媒体、利用するモデル、
接続する道具・アクセス先は後で決めます。透明性の方針も検討中です。
基礎設計では、これらの具体値に依存しない境界・所有・実行順を定義しました。
未決の項目を理由に、心理的な専用ルールや暫定の固定人格を増やしません。

## 実装順

| 段階 | 作るもの | 検証すること |
|---|---|---|
| 0（このブランチ） | Goのホスト、Makefile、Docker、CI、基礎設計、合意済み仕様の反映 | 起動・bind失敗・health・終了、build / lint / race / coverage |
| 1 | snapshot / proposal / commitment、mindの単一所有、Channel生命周期 | 二つの思考が重なり、片方が止まっても他方が進む。取消後の結果を採用しない |
| 2 | 人格と4つの内面、体験文脈の形成、記憶ポート | 人格値が主体に漏れない。気分・意図が会話をまたぐ。関心に忌避を表せる |
| 3 | 行為のGateway、錠、予測分離、承認待ち | すべてのChannelが同じ境界を通る。未知の道具・無承認の更新を実行しない |
| 4 | 保存・outbox、回復、状態の投影、管理用観察 | 未保存の更新を実行しない。結果不明の送信を重複しない。外部状態に機密が出ない |
| 5 | 選定したLLMと媒体・道具を実接続 | 内面を伴う対話・自律行動の一連の振る舞い。細かい合格条件はレビューで決定 |

これはコードの依存順であり、人格のロードマップではありません。
本番の一連の振る舞いは感情・記憶・関心・目標を備えた段階から始めます。
LLMのないfake Channelで並列性を検証しても、自律思考が完成したとは扱いません。

## 必須の実行検証

テストはtable-drivenとし、状態を共有しないケースには `t.Parallel()` を使います。
時刻・乱数・モデル・道具は消費側から差し替えられるようにし、sleepで順序を祈るテストにしません。
開始・完了の同期点で順序を作り、race detectorも使います。

後続の実装では次を含めます。

- 遅いActionがあってもInteractionが候補を返せる。着想があふれても呼びかけが扱われる。
- snapshotのmap / sliceを変更しても共有状態が変わらない。
- 古い世代、変更された依存対象、重複イベントを適切に扱う。
- 配信から遅れたChannelが採用済みの意図と状態を再取得する。
- 同じ対象への更新を直列化し、異なる対象の仕事は同時に進む。
- predictionから外部更新・長期記憶更新をできない。
- 承認後の引数変更、別行為への承認流用、秘密を含む検索語を拒否する。
- 外部成功後のtimeout、保存失敗、復旧中のクラッシュで重複送信しない。
- 最低応答と本返答が競合しても二重送信しない。
- 停止でworker / 子プロセス / listenerを回収する。

internalパッケージのカバレッジは約100%を維持し、薄いプロセス入口は実バイナリで確認します。
成功するfakeだけで達成したことにせず、
重要な不変条件・障害時の挙動・実際の起動経路を確認します。

## 足場の検証と撤去

LLMに任せたい判断はChannel側の実装へ寄せ、状態保持やスコアの足場と境界を分けます。
モデル変更後も同じ振る舞いの観察例を使い、外せる足場を評価します。
錠の発動回数は成功指標にせず、正常な理性で止まれなかった原因の観察に使います。
コスト・遅延・トークン量と、人としての疲れ・飽きは別に測ります。
