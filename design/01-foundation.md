# 01. 構成と責務

## 設計の中心

一人の Akari を一つの Go プロセスで動かします。Channel の思考は並列、
内面の共有状態への反映は順序づけます。DBやMCPサーバーを主体の分割単位にしません。
まず単一プロセスで一貫性を検証し、負荷を測らずにサービスを分割しません。

人格の広さとインフラの同時実行数は別です。広さは意識に上げる内容と疲れに効き、
インフラ上限はメモリ・接続・コストの最終的な錠です。通常の抑制は理性に任せます。

## 責務の分割

以下は全体のパッケージ計画です。mind / thought / action と、人格・感情・記憶・関心・目標の状態基盤を実装しました。
空のインターフェース群を先に実装して固定しません。
ポートは消費側のパッケージに、必要になる時点で小さく定義します。

| パッケージ | 責務 | 持たないもの |
|---|---|---|
| meaning | 意味空間の版と座標、比較、符号化のポート | 特定のembeddingプロバイダー |
| persona | 起動時固定の人格ベクトル、軸の順序とバージョン、検証 | ホットリロード、主体向け数値参照API |
| emotion | 感情の評価結果、持続する気分、共感の反映 | 固定の感情語列挙、疲れ |
| memory | 想起・整理・忘却・覚えたい意志、Kisekiの意味 | ORM型、完全ログの無条件想起 |
| interest | 対象への親和・忌避、進展の手応え | 全判断を独占する単一スコア |
| goal | 願い・意図・手順、コミットの整合 | 性格の成長 |
| mind | 状態の所有、選ぶ・配る・束ねる・決める・綴る | 外部API待ち、内容を考える巨大なLLM司令塔 |
| thought | Channelの生命周期と並列計算、候補の生成 | 共有状態への直接書き込み、MCP生接続 |
| action | 行為の共通境界、承認・機密・実行・結果 | 対象ごとの心理的振る舞いルール |
| conversation | 会話の場、受け手、出力順、最低応答の監視 | すべての情報取得の代理実行 |
| runtime | 入力・内部イベント、起動・取消・停止、資源上限 | 人格の都合による安全条件変更 |
| 各アダプター | LLM、MCP、媒体、保存、管理画面への変換 | 内面のモデルや意思決定の所有 |

依存の方向は「外側のアダプター → 利用側のポート → 内面・行為の契約」です。
内面からHTTP・MCP SDK・DBの型を参照しません。依存の組み立ては入口で明示的に行います。
一つの巨大な ports パッケージ、全サービスを引けるコンテナ、暗黙のグローバル状態は作りません。

## Channelとモデル呼び出し

Channelは「思考系列の主体」であり、goroutineやLLM呼び出しそのものではありません。
一つのChannelが複数のモデル呼び出しを行ってよく、モデル待機中に別Channelが進めます。
Goのchannel型とは区別し、実行基盤では系列の識別子と世代を `Token` に持たせます。
具体的なChannelの種類・体験文脈は後続で型にします。

Interaction、Actionの統括、情動評価、記憶想起は常設です。
個々の仕事・着想は対象ごとの子系列として作り、終われば解放します。
Action統括が一つでも、個々の仕事を直列に処理する意味ではありません。
対外発話はInteractionが整え、Actionの結果は内部の観察として返します。

モデル要求に人格ベクトルや管理設定を丸ごと注入しません。
モデルは体験・気分・関心・意図・関係の文脈を受け取り、値はその文脈の形成や処理に効かせます。
Akariに自分の値を尋ねる管理ツールは渡しません。

LLMの出力は未確定の提案です。構造・出所・参照版を検証し、実行権限として扱いません。
認知の選択方式とプロバイダーは独立に交換できます。

## 維持する開発基盤

`akari/go.mod` を唯一のGoモジュールとし、GoLandで `akari/` を開けば開発できます。
実行コマンドはMakefileに集約します。基礎ホストは標準ライブラリだけで動きます。
Dockerは非rootのランタイム、read-only root filesystem、書き込み可能なデータ用volumeを備えます。
このvolumeは後続の保存用予約であり、現在のホストは人格を保存しません。
運用環境の秘密は起動時に外から渡し、人格・ログ・イメージへ含めません。
