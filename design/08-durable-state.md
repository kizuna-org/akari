# 08. 保存・復元・outbox

[04](./04-continuity.md) の保存順序を、実サービスを使わずに検証できる基礎として実装しました。
DB製品、本番の保存形式、媒体やモデルを選定したことにはしません。
ローカルファイルのアダプターはGoのポートから交換できます。

## 一つの採用単位

`continuity.Owner` が内面のWorkspaceと実行記録を所有します。
変更可能なWorkspaceを外へ渡さず、`Snapshot`と`Recall`だけを思考の材料にします。
`Export`は人格の設定とoutboxを含む管理用のコピーです。モデルには渡しません。

`Adopt`はコピー上で提案を検証し、同じ採用版の内面・記憶・共有文脈・実行待ち行為を
`Frame`として一回で保存します。保存が成功するまで新しい体験を公開しません。
行為の正規化・宛先・機密・容量の検証に失敗した場合も、提案の一部だけを採用しません。
予測は従来どおり実状態へコミットできません。

保存の`Sequence`は採用版とは別です。行為の承認・開始・結果の記録でも進みます。
保存先は期待するSequenceと一致する場合だけ、次のFrameへ原子的に置き換えます。
古い所有者による保存は拒否します。これは複数プロセスで一人を稼働させる分散実行の設計ではなく、
一つのインストールにつき一つの稼働Ownerを使う前提です。

保存処理は一つに制限し、追加の変更を無制限に待たせず`ErrBusy`で返します。
保存中も最後に採用した状態を読むことができます。保存にはホストの期限を与えます。
保存結果が不確かな場合は新しい採用とdispatchを停止し、再読込まで続行しません。
別の候補として行為を作り直して、自動再送することもruntime側で行いません。

## 思考の採用と取消

Supervisorは消費側の`Workspace`ポートを通して、メモリだけの所有者と保存を伴うOwnerを扱います。
`Accept`はその所有者の`CommitContext`を使います。
同じ採用に行為を含める場合、trusted runtimeが`AcceptWith`から`Owner.Adopt`を呼びます。
そのときも公開されたpreviewではなく、Supervisorが保持する提案のコピーを使います。

採用中はその完了を二度採用・破棄できませんが、Supervisorのロックで保存を待ちません。
別Channelの開始・取消が進み、停止は保存中の採用も待ちます。
保存前の取消は新しい状態を残しません。保存済みの採用を、後から取消で巻き戻しません。
保存先の返答が曖昧なら、成功・失敗を推測せず復元で確かめます。

## 行為の実行記録

行為は信頼されたGatewayの`Prepare`で正規化し、道具名・引数・作用・宛先・競合対象・出所・
承認の要否をコピーして保存します。関数やプロセス内のPendingを保存しません。
承認は管理側だけが行い、保存された一つの行為に結び付けます。

| 保存状態 | 次の扱い |
|---|---|
| Queued | 明示したdispatchで再正規化・再検証。承認が必要なら保存済みの承認を確認 |
| Running | Gatewayへ渡す前に保存する。再起動時はUnknownへ保存し直し、自動実行しない |
| Succeeded | 完了として保持。同じIDは再実行・再採用できない |
| NotExecuted | 実行前の取消・拒否、または照合で未実行と証明した結果。同じIDは再実行しない |
| Unknown | 自動再送せず、管理側のResolverによる結果照合を待つ |

dispatchは先にRunningを保存し、保存成功後だけGatewayを実行します。
実行待ちの対象ロック・実行枠、宛先、機密合意、承認は既存の共通境界を通します。
再正規化で保存した行為の内容が変わった場合は実行しません。
機密合意は最新の採用状態を参照し、実行枠の取得後にも確認します。

Gatewayの`ExecuteIdentified`は、保存したインストールIDと行為IDからなる安定したキーを渡します。
`Operation.CallWithKey`に対応するアダプターは、そのキーを外部の冪等性機能へ渡せます。
外部側の冪等性を持たないアダプターも使えますが、exactly-onceの保証を追加しません。
外部処理を待つ間は保存の枠を解放し、別の採用や別対象の行為を進められます。
対象ごとの競合はGatewayが順序づけます。

実行前の取消はNotExecuted、外部呼び出し後のエラー・panicはUnknownです。
呼び出し側が取り消されても、結果の保存には別の有界なcleanup期限を使います。
結果を書けなかった場合もOwnerを停止し、再起動ではRunningをUnknownへ回復します。
外部が成功していた場合、結果が未保存でも自動で同じ行為を送り直しません。

`Resolver.Lookup`は同じキーによる照合だけの能力です。行為を実行してはいけません。
SucceededかNotExecutedを証明した場合だけ、その結果を保存します。
実サービスの照合アダプターも、外部アクセスにはGatewayの読み取り境界を使う契約です。
Queuedへの自動的な復帰や、Unknownの楽観的な成功判定は置きません。

## ローカル保存と復元

`persistence.File`はUnixのローカルファイルシステム向けの検証用アダプターです。
保存先はインストール専用のディレクトリを与えます。新規ディレクトリは0700、ファイルは0600です。
現在のJSON schema 1は基礎実装の形式で、本番のDBや移行方式を固定しません。
秘密情報や原文を標準ログへ出す処理は加えていません。保存内容は暗号化していません。

OSの排他ロック → 保存Sequenceの照合 → 同じディレクトリの一時ファイルへの書込み →
ファイルfsync → rename → ディレクトリfsyncの順です。
rename以降は取消で巻き戻さず、保存の確定を試みます。そこで失敗した場合も成功と断定しません。
破損したJSON、未知のフィールド、余分な末尾、16MiBを超えるデータを拒否します。
ロック待ちは100msまでの有界な待機で、心理的な疲れとは無関係です。

`mind.Restore`はschema、人格IDと固定設定全体、各柱と共有文脈の版、内面の妥当性、
短期記憶と記録の整合、資源容量を検査します。不一致を無視して新しい人格で起動しません。
保留中の意図と手順位置を復元しますが、goroutine・購読・Channelの世代は復元しません。
復元後のChannelは新しいSupervisorで起動します。

## 確認した境界と残り

保存前・保存後の返答不明、実行開始記録の前後、外部成功と結果保存の間に失敗を注入して検証しました。
別のテストプロセスを外部操作の直前・直後で強制終了し、実ファイルからの復元と再送拒否も確認しました。
これはプロセスクラッシュの検証で、物理的な電源断・ディスク故障や、実サービスの冪等性の実証ではありません。

完了したIDもoutboxに残して再利用を防ぎ、設定した容量を超えた採用を拒否します。
保存記録の削除・保管期限・安全な圧縮、バックアップ、形式移行、承認の時間による失効は後続です。
この容量は運用上の錠で、Kisekiの忘却や人格の意図数に置き換えません。
ディスクI/OそのものがOS内で停止した場合、Goのcontextだけでfsyncを強制中断できるとは扱いません。

ホストの起動・終了への配線、具体的な常設Channel、管理用の回復状態表示はまだ接続していません。
ホストはhealthだけを返します。実LLM・MCP・有料サービス・認証情報は使っていません。
